## Response to Reviewer（逐条回应审查者）

### UX-1：0 回应空状态  
【接受】

审查者是对的。原方案低估了“心愿无人回应”的伤害，这不是普通空状态，而是“我被世界忽略”的放大器。

修订设计：0 回应不展示为“没人祝福你”，而是进入“静候池”。

具体机制：

1. 发出心愿后，立即给用户一个非社交兜底结果：  
   “你的心愿已被收好。先敲 9 下木鱼，为它安放一点好运。”  
   用户先完成自我仪式，避免第一反馈依赖他人。

2. 公开广场不显示“0 祝福”计数。  
   心愿卡只显示状态：  
   “正在等有缘人路过” / “已被安放” / “今日好运中”。

3. 若 24 小时无人回应，系统不伪装真人送祝福，而是触发“归档式安慰”：  
   “这条心愿今天没有遇到路过的人，但你为它敲过的 9 下已经留下。”  
   可选按钮：  
   “再放一天” / “收进口袋” / “只留给自己”。

4. 不使用系统账号冒充用户。  
   系统只能提供“仪式反馈”，不能提供“社交反馈”。

立场变化：心愿发布不能以“获得他人回应”为唯一成功态。MVP 必须验证的是“自我仪式 + 少量真实回应”是否足够，而不是纯广场众筹。

### UX-2：双货币认知成本高  
【接受】

双货币方案需要砍。好运值 / 积福值会让用户开始算账，违背零焦虑。

修订为单一概念：“好运”。

但好运有两个动作，不是两个资产：

1. “攒好运”：自己敲木鱼、许愿、安放心愿。  
2. “送好运”：把自己今天的一点好运送给别人。

用户不需要理解账户系统，只需要理解一句隐喻：  
“好运不是花掉的，送出去会留下福气。”

产品上不显示复杂余额，只显示轻量状态：

- 今日已敲：9 下  
- 今日已送：3 次  
- 收到好运：5 份

如果保留“积福”，只能作为事后称号，例如“今日积福 3 次”，不能作为前置货币规则。

立场变化：从“双货币激励系统”改为“单一好运语义 + 行为记录”。核心不是经济系统，而是低认知仪式感。

### UX-3：第一次发起心愿流程缺失  
【接受】

这是关键漏斗，必须极简。

第一次流程修订如下：

1. 入口不是“发起众筹”，而是“放一个心愿”。  
   按钮文案：`放下一个心愿`

2. 进入后先选模板，不从空白输入开始：  
   - 求顺利  
   - 求安心  
   - 求被看见  
   - 求身体好一点  
   - 求考试 / 面试 / 工作顺一点  
   - 自己写

3. 文本默认生成，可编辑：  
   “希望接下来这件事顺一点。”  
   用户可以不写具体隐私。

4. 公开性默认是“半匿名公开”。  
   显示为：  
   “一位路过的人”  
   用户可切换：  
   - 只给自己  
   - 放到广场  
   - 生成链接给朋友

5. 发出后不直接丢到冷清广场，而进入仪式页：  
   用户敲 9 下木鱼，看到心愿被“放入好运池”。

6. 完成后给两个去向：  
   - “看看别人的心愿，送一点好运”  
   - “收好，晚点再看”

关键原则：第一次发心愿的成功反馈必须由自己完成，而不是等别人完成。

### 业务-1：低频产品如何维持广场“活”  
【承认为权衡】

这个矛盾成立。低频情绪产品很难维持传统意义上的实时广场。

因此我重新定义“活”：  
不是实时刷新的社交流，而是“用户打开时能看到最近有人留下过真实痕迹，并且自己送出的好运能立刻产生反馈”。

最低活跃度假设：

[假设: MVP 阶段只服务一个小圈层或一个明确场景，不做开放大广场。]

一个小型好运池如果每天有：

- 30-50 条真实心愿  
- 100-200 次真实送好运  
- 每条心愿中位数 2-3 个回应  
- 用户打开时前 20 张卡里至少 15 张来自过去 72 小时

就可以感觉“不死”。它不需要像微博实时流，但不能像留言板荒废。

个人项目怎么达到：

1. 不做全网广场，先做“主题池”：  
   例如“考前好运池”“求职好运池”“病中陪伴池”“深夜安心池”。

2. 每次只开放一个主题池，集中流量。  
   分散广场会更冷，主题池能提高匹配感。

3. 用固定时段制造轻活跃：  
   例如每天 22:00 的“晚安心愿池”。  
   低频产品需要节律，不适合全天候空场。

4. MVP 的活跃标准不是 DAU，而是“心愿被真实回应率”。  
   若 48 小时内真实回应率低于 60%，广场机制判失败。

这是权衡：牺牲“开放平台想象”，换取小范围真实密度。

### 业务-2：为什么不用微信 / 微博 / 小红书  
【反驳】

已有平台能完成“祝福”，但不能低成本完成“脆弱表达”。

反推理如下：

1. 微信适合熟人，但用户许愿等于向熟人暴露状态。  
   很多心理慰藉需求恰恰是不想麻烦朋友、不想解释原因、不想被追问。

2. 微博 / 小红书有流量和评论，但表达会被表演化。  
   用户容易担心措辞、头像、人设、互动量，焦虑成本高。

3. 锦鲤转发是围观型好运，不是点对点安放。  
   它强调“我求中”，不是“我被轻轻回应”。

4. 新 H5 的独特价值不是功能稀缺，而是场域稀缺：  
   一个默认匿名、低表达压力、无金钱、无熟人审视、无转发 KPI 的小仪式场。

转移成本的答案：  
不能要求用户长期迁移，只能在特定情绪时刻打开。它不是替代微信，而是补微信做不了的场景：  
“我需要一点回应，但不想真的向任何具体的人求助。”

因此产品形态也应是 H5 / 小程序轻入口，而不是重 App。

### 业务-3：冷启动没解决前 MVP 能验证什么  
【接受】

冷启动不是待研究，是生死前提。系统账号送好运会污染验证，我收回“系统兜底社交反馈”的任何可能性。

MVP 只能验证三件事：

1. 用户是否愿意放下一个半匿名心愿。  
   指标：访问到发心愿转化率、模板选择率、放弃点。

2. 用户是否愿意给陌生人的心愿送好运。  
   指标：看见心愿后的送好运率、连续送出次数、是否写短祝福。

3. 在少量真实回应下，用户是否愿意回来查看。  
   指标：收到真实回应后的 24/72 小时回访率。

MVP 不能验证：

- 大规模平台网络效应  
- 长期留存  
- 开放广场自然繁荣  
- 商业化

冷启动做法必须是真人小圈层：

- 找 100-300 个种子用户  
- 限定一个主题池  
- 限定 3-7 天实验窗口  
- 不用机器人冒充祝福  
- 可以由运营邀请真人参与，但必须标记为真实用户行为

数据可信的边界：  
如果种子池里都无法产生互赠，开放平台更不可能成立；如果种子池成立，也只能证明“特定场景小池可行”，不能证明平台级成立。

## Revised Proposal（修订后立场）

[REVISED] 1. “零金钱好运慰藉”是真需求，但不是“众筹平台”需求，而是“匿名低压表达 + 轻量真实回应 + 自我仪式兜底”的情绪产品需求。它比电子木鱼多一点社会回声，比朋友圈少很多暴露压力。

[REVISED] 2. 目标用户表面很大，真实可用盘子应按场景切分，而不是按泛焦虑人群估算。优先场景是考试、求职、病痛、失眠、低谷、重大决定前。真实意愿不是“每天敲木鱼”，而是“焦虑高峰时愿意花 30 秒放下心愿，并偶尔给别人一点好运”。

[REVISED] 3. 不可替代点不是游戏化货币，也不是广场本身，而是“无需金钱、无需熟人暴露、无需强转发的半匿名祝福场”。如果这个场域感做不出来，产品不值得做。

## Evidence and Rationale（证据与理由）

[假设: 很多人有轻度表达需求，但不愿把脆弱状态发到熟人社交网络。]  
因此产品必须降低表达风险，而不是强化传播。

[假设: 陌生人祝福的价值来自“真实有人路过”，不是来自数量。]  
所以 1-3 个真实回应可能比 99 个系统祝福更有效。

[假设: 用户对好运产品的理解主要靠隐喻，不靠规则。]  
所以应砍掉复杂积分，把系统藏在动作之后。

[假设: 低频情绪产品无法支撑全时开放广场。]  
所以 MVP 应集中在主题池和限时实验，而不是一开始做平台。

[假设: 如果 100-300 人的小池都无法自然互赠，说明核心闭环弱。]  
这比做一个看似完整但靠假活跃撑起的广场更有验证价值。

## Trade-offs Acknowledged（权衡）

1. 放弃“众筹平台”叙事，改成“好运池 / 心愿池”。平台想象变小，但定位更真实。

2. 放弃双货币成长系统，降低游戏深度，换取低认知门槛。

3. 放弃系统账号假祝福，冷启动更难，但数据更干净。

4. 放弃全网开放广场，先做主题小池，牺牲规模感，换取真实密度。

5. 0 回应用自我仪式兜底，不伪造社交温度；这会降低即时爽感，但避免伤害用户。
