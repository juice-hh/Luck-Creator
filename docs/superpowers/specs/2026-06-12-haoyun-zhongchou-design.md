## 〇、辩论后最终方向（2026-06-22 确认，优先级最高）

经过一轮 5 阶段跨模型对抗辩论（记录见 `debates/haoyun-zhongchou-platform/`），用户做出最终产品决策。**本节是对下文的修订总纲，与下文冲突时以本节为准：**

1. **保留游戏形式**（最终决定）：核心是"自己玩小游戏攒好运 → 好运槽积累 → 凑满'好运达成'"的**真实积攒/收获手感与反馈**。不把产品砍成纯情绪工具——游戏性是体验的核心。
2. **保留双向 slogan**（甲方案）：自己攒好运（收获**运气**）+ 给别人送好运（收获**福气**：福气卡）。两侧都做。
3. **"有趣"是第一命门**：赌"一部分人因为好玩而使用和分享"，前提是**必须把小游戏和福气卡做得真有趣、真想截图**。小游戏不够有趣是头号风险，需创意专场死磕（见第七节）。
4. **从辩论吸收的护栏（不削弱游戏性，只防翻车）**：
   - **不伪造真人**：任何"收到他人祝福/送好运"必须是真人，或诚实标注（如"过来人的历史留言/非实时"）；空状态诚实呈现，绝不用机器人假装热闹。
   - **社交线做成异步**：广场/送好运不依赖"同时在线"——可给同主题的历史/未来有效心愿送好运、对方异步收到（"异步时间窗池"），破解"低频产品撑不起实时广场"。
   - **先做有趣的小验证再铺开**：第一版先把"一个攒好运小游戏 + 福气卡"做到真好玩、真想晒，验证"有趣"成立，再加广场/更多社交（见第十二节 MVP 分层）。
   - **零金钱、零焦虑** 仍是底线（与下文理念一致）。
5. **名字**：好运池。"众筹"作为内部隐喻可保留，不作为对外产品名。

## 一、一句话定位

一个**游戏化的"好运池"**：用户为自己许下心愿、发起好运众筹；自己做仪式、或被他人祝福，攒满好运后"好运达成"。

- **捐赠者收获福气**——主动把好运送给别人，就是积德行善，收获福气（福气卡 + 积福值）。
- **受捐者收获运气**——许下心愿、收到他人祝福，收获运气与"被惦记"的温度。

**它不是**：增长黑客式的砍一刀裂变工具。
**它是**：一个**心理慰藉产品**——帮人积攒好运、减轻压力、获得心理寄托。

---

## 二、核心理念（凌驾于一切功能之上）

这几条是产品的"宪法"，任何具体设计与之冲突时，以理念为准：

1. **心理慰藉 > 增长裂变。** 用户来这儿的根本目的是积攒好运、减压、找寄托。任何会制造焦虑的机制（逼迫拉人、倒计时、签到打卡、过期失败）一律不要。
2. **给予是快乐，索取才焦虑。** 社交的主方向是"我主动送好运给别人"（积福、温暖），而不是"我求别人助力我"（人情债、压力）。
3. **好运是可以互相赠予的"心意"，不是需要乞讨的"资源"。** "求"被重新包装成"许愿 + 邀请被祝福"，不羞耻、不焦虑。
4. **节奏由"心意/付出"决定，不由"时间"决定。** 没有任何按天的额度、签到、连胜（streak）。急需好运的人今晚就能攒满，安静等待的人也永远不会"失败"。
5. **视觉与情感调性 = 玄学仪式感 + 网络热梗。** 达成证书、福气卡都融合小红书/抖音的热门梗图、表情包，天生适合截图分享。
6. **Simplicity First（含义要诚实）。** "最小"指**不做核心循环之外的任何功能**，而不是"功能越少越好"。本产品的核心循环**天然包含"给予/广场/福气卡"**——没有它们就不叫"好运众筹"，只是个单机木鱼。所以这三者是核心、不可砍；真正要砍的是它们之上的**养成/配置/灵活性**（合成、交易、加成、排行榜、签到、为未用功能预建字段等）。第十二节的 MVP 即据此界定。
7. **不伪造真人（辩论新增）。** 任何"他人祝福/送好运"必须是真人或诚实标注；空状态诚实呈现，绝不用系统账号/机器人冒充真人制造虚假热闹。这是信任底线。
8. **有趣优先（辩论新增）。** "一部分人因为好玩而来、而分享"是本产品的增长赌注；小游戏与福气卡**必须做到真有趣、真想截图**，否则零焦虑会退化成"平淡无聊"。"有趣"与"零焦虑"并不冲突——冲突的是机制化焦虑（积分/排行/抽卡/签到），不是幽默与爽感本身。

## 三、核心循环

```
  发起者许愿 ──▶ 发起「好运众筹」(绑定具体心愿，需攒满 N 点好运)
                          │
        ┌─────────────────┴─────────────────┐
        ▼                                     ▼
   自己做仪式攒好运                       他人赠予好运
   (敲木鱼等小游戏，不封顶)             (陌生人/好友送，不封顶)
        └─────────────────┬─────────────────┘
                          ▼
                  好运槽持续积累
                          ▼
                  ✨ 好运达成（水到渠成，非紧逼任务）✨
            ┌──────────────┴───────────────┐
            ▼                               ▼
   发起者：好运达成证书(梗图/仪式感)      送好运的一方：每次送出即「积福」
          + 好运值累积成长                  → 获得福气卡 + 积福值
          + (也能开一张福气卡)
```

**关键不变量**：

- 攒好运的两个来源（自己攒 / 他人送）**都不设时间限制、不设每日上限**。
- 心愿**无 deadline、不会过期、不会失败**——他人助力永远是"加速的锦上添花"，不是"救命的雪中送炭"。
- **任何人送出好运的那一刻，对送出方永远是"积福"**（这是对冲社交焦虑的核心机制，见第五节）。

**"自己能无限攒满，为什么还需要社交/广场？"——这个张力的解法（重要）**：

1. **广场由"给予侧"驱动，不由"索取侧"驱动。** 送好运是助力者**积福、获得福气卡的唯一途径**（由第四节"双货币模型"从机制上锁死：积福值唯一来自给予，自攒换不来福气卡）。所以哪怕发起者完全能自攒，仍会有大量用户主动涌入广场去"送"——动机是**自己想积福、想得卡**，而不是"被迫帮人"。广场的活力来自给予者，正好契合"给予是快乐"。需求侧（被祝福）只是被顺带满足。
2. **自攒永远能独自达成（满足急需、零焦虑），但"被祝福"让达成更圆满。** 被有缘人祝福过的心愿，**达成证书更特别**——会带上"X 位有缘人为你送过好运"的情感印记。社交是让心愿**更有温度、更圆满**，而不是**完成的必需条件**。

> 一句话：自攒解决"我能掌控、零焦虑"，社交解决"被惦记的温度 + 给予者的积福"。两者各有不可替代的价值，不互相架空。

## 四、两种角色与回报

| 角色 | 别名 | 做什么 | 收获 |
|---|---|---|---|
| 发起者 | 受捐者 | 许愿、做仪式自攒、收他人祝福 | 收获**运气**：好运达成 |
| 助力者 | 捐赠者 | 给陌生人/好友送好运 | 收获**福气**：福气卡 + 积福值 |

> 同一个用户随时可以在两种角色间切换：既能为自己许愿，也能去给别人送好运。

### 双货币模型（产品骨架，锁死广场动机）

整个系统由**两套互不替代的货币**支撑，正好对应 slogan 的两半：

| 货币 | 对应 | **来源** | 用途 |
|---|---|---|---|
| **好运值** | 受捐者收获**运气** | 自己做仪式攒 + 他人赠予 | 填满自己心愿的好运槽 → 达成；沉淀为「好运等级」 |
| **积福值** | 捐赠者收获**福气** | **唯一来自"把好运送给他人"这一动作**（自攒、达成均不产生积福值） | 获得福气卡（保底机制，见第六节） |

> **这是堵住"自攒架空广场"的关键机制**：想达成心愿，靠好运值即可（能自给自足、零焦虑）；但**想得福气卡，就必须去给予别人**——自己闷头敲木鱼**永远换不来一张福气卡**。于是"想集卡/想积福"的人只能涌向广场和好友去送好运。**广场的供给侧由"给予才得福气"从机制上锁死，不靠自觉、不会被自攒替代。**

### 发起者达成时的回报（采纳 A + C 为主，B 为辅；砍掉 D）

- **A · 好运达成证书 + 仪式感（主）**：绑定具体心愿（求上岸 / 脱单 / 不脱发 / 求暴富……），达成后给一张**可分享的「好运达成卡」+ 仪式动画**。证书与文案**融合网络热梗、表情包**，主打玄学仪式感 + 好笑 + 想截图发出去。
- **C · 好运值累积成长（主）**：达成的好运沉淀为账号的**好运等级 / 锦鲤值**，越攒越高，有等级、称号、（后续）排行榜。这是长期、健康的留存来源。
  - **与"签到/连胜"的本质区别**（必须守住）：好运值**只增不减、永不清零、断了不掉、从不弹窗催你回来**。它记录"你一共积了多少福/运"，是一个温暖的纪念，而非紧箍咒。签到 streak 之所以是焦虑机制，是因为它用"别断了连续 30 天！"的**损失厌恶**绑架你——好运值不制造任何"会失去"的恐惧，所以是健康的。
- **B · 达成纪念卡（辅，已重构以消除矛盾）**：达成后发起者获得一张**「好运达成纪念卡」**——它属于 **A（运气侧、可晒、梗图仪式感）**，是达成证书的卡片化形态，**不是福气卡，也不计积福值**。
  - 为什么不直接给福气卡：福气卡是"给予才得福气"的专属回报（见双货币模型），若发起者自攒达成也能拿福气卡，就打穿了"积福值唯一来自给予"的骨架、让广场动机重新塌掉。所以发起者那张卡走**独立的纪念卡**池子，满足"达成也能开张卡晒一晒"的爽感，又不破坏机制。
- **D · 解锁更高级心愿** —— **砍掉**（本质是 C 的包装，避免过度设计，核心循环跑通后再议）。

## 五、社交模式：求助力与送祝福"两全其美"

**统一为一个核心动作：「送好运」。** "求"和"送"是同一枚硬币的两面。

```
  送祝福（主动给予 → 积福）            求助力（公开心愿 → 邀请被祝福）
  ├─ 在广场给陌生人送好运              ├─ 把自己的心愿安静分享给好友
  ├─ 主动给好友的心愿送好运            └─ 心愿也出现在广场，等有缘人路过
  └─ 你=捐赠者，收获福气               你=受捐者，收获被惦记的运气

         ↑ 无论哪个入口，"送"的一方永远在「积福」↑
```

### 焦虑拆解（这是本设计的核心价值）

"求助力"之所以让人焦虑，来自三处，逐条拆掉而非砍掉：

| 焦虑来源 | 拆解设计 |
|---|---|
| ① **欠人情债**（"求了人得还"） | **帮你的人自己也即时积福**（得福气卡 + 积福值）。求助力 = 给对方递一次"积德行善"的机会，双向获益，人情债被对冲。 |
| ② **怕完不成**（"求不到就完蛋"） | 心愿**无 deadline、不失败、不过期**；且**自己随时能攒**。助力永远是加速，不是救命。 |
| ③ **怕打扰、尴尬** | **柔性表达**：分享文案是"我在攒好运求面试上岸🙏 路过给我敲两下木鱼吧（你也能积福气）"，**无倒计时、无逼迫式进度条**。 |

### 三个入口，一种善意

- **广场（第一版核心）**：陌生人互祝。看到陌生人的心愿，顺手送几点好运——你积福、他得运，双方零人情负担。**这是最契合"零焦虑"的入口，故提到第一版核心**（不再是二期）。广场的供给侧（愿意送的人）由"积福 + 得福气卡"驱动，详见第三节张力解法。
- **主动给好友送**：看到好友的心愿，主动送上祝福。
- **分享自己的心愿**：把心愿柔性分享给好友，愿意就送、不愿也无所谓。

### 留存靠情感，不靠签到

去掉一切签到 / streak。留存来自健康的牵挂：

- 想看看自己的心愿有没有被陌生人/好友祝福；
- 想去给别人积点福；
- 想补齐图鉴里还没收集到的福气卡（**零挫败收集**，见第六节——是"想看看今天又开到什么好笑卡"的轻松牵挂，不是"抽不到的焦虑"）。

## 六、福气卡（助力者的回报，"福气"的载体）

采纳：**纯收藏梗卡 + 稀有度 + 图鉴**；砍掉合成 / 交易 / 加成。

- **纯收藏梗卡**：拉屎通畅卡、考试蒙对卡、一路绿灯卡、外卖不洒卡…… 价值在**好笑 + 收集欲 + 晒朋友圈**，**无任何实际功能/加成**。
- **稀有度**：普通 / 稀有 / 传说（保留，给收集欲与晒卡理由）。
- **图鉴**：可收集、可凑套、可查看进度。
- **回赠（一期，采纳"丙"方案）**：**只有重复的卡能回赠给好友**——既满足"把好运分享给朋友"的情感、又消化重复卡、又不破坏稀有度体系。
- **砍掉**：合成、交易市场、卡牌套装加成（那是另一个重度游戏，违背 Simplicity First）。

### 零挫败收集（采纳方案"甲"，守住"零焦虑"理念）

稀有度/图鉴很容易滑向 FOMO 养成焦虑（"传说卡抽不到""还差一张集不齐"），与"减压、零焦虑"定位冲突。因此本设计明确约束：

- **没有"抽不到"的挫败**：传说卡不靠极低掉率制造稀缺。稀有度只决定"出现的惊喜感/好笑程度分级"，不制造"肝不出来"的痛苦。
- **图鉴保证可补齐**：任何卡都能通过**非纯随机**的方式拿到（如保底机制：积福到一定量必得未拥有的卡），不存在"永远差一张"的死结。
- **绝不催促**：不弹"还差 1 张就集齐了，快来抽！"这类 FOMO 文案；图鉴进度是"自己看着开心"的呈现，不是逼迫钩子。

> **隐藏耦合提醒**：回赠"仅重复卡"的判定依赖图鉴的"已拥有/重复"去重逻辑，因此**图鉴与回赠绑定同期实现**，不可一个上线一个延后。

## 七、助力小游戏（待创意专场，但框架先定）

> ✅ **创意专场已定稿（2026-06-22）**：游戏池 = 敲木鱼 / 戳穿霉运泡泡 / 投喂锦鲤（解压+治愈）。**V0 主打做透「敲木鱼 Pro」一个**，另两个进 V1（见第十二节路径）。

### "有趣"的 4 根设计支柱（每个小游戏都要过这关）
1. **核心玩具感**：无目标也想点（解压如捏泡泡纸）。
2. **Juice 汁水反馈**：夸张即时反馈——音效升调、金光粒子、数字飞、轻震动。
3. **意外性**：随机惊喜（暴击/成精/显灵/翻车彩蛋），杜绝"第10下就腻"。
4. **想截图的瞬间**：一局产出"荒诞到想发群"的东西＝传播货币。

### V0 主打：敲木鱼 Pro（深化设计）
- **核心玩具**：连点木鱼，每下"咚"+「功德+1」金色飘字 + 轻震动；连击加速 → 木鱼泛金光、音调升高、功德数字越飞越大。
- **意外性（随机触发）**：⚡功德暴击"×8 金光炸屏"；🪵木鱼成精（长眼/咧嘴/飘起转圈/吐槽"敲轻点疼"）；✨显灵（极小概率佛光+功德雨+掉**稀有福气卡**）；🤡翻车彩蛋（"功德 −1，逗你的"）。
- **想截图的瞬间（两个都要）**：
  1. **功德战报**（一局结束自动生成）：荒诞数据卡——"你今天敲了 327 下，超过全国 89% 的电子修行人；佛祖已收到，但建议你也去睡觉"。
  2. **福气卡**：随战报附赠一张（见下）。

### 福气卡 = 另一半"想截图"引擎
笑点公式 = **庄严卡面（烫金/佛光/毛笔字）× 沙雕内容**。分类示例：
- 🚽 生活窘境救急：拉屎通畅卡 / 外卖不洒卡 / 红灯变绿卡 / 消息秒回卡 / WiFi 满格卡
- 💰 玄学暴富：祖坟冒青烟卡 / 中奖绝缘体豁免卡
- 🫠 自嘲：已读不回免疫卡 / emo 暂停卡 / 周一消失卡
- 🌟 稀有传说：天选之子卡 / 佛祖亲签卡（敲木鱼显灵才掉）
- **关键**：卡上印用户当时心愿/数据 → 独一无二 → 才想晒。

### 第一版游戏池（均吃同一套框架；V0 先只做敲木鱼 Pro）

| 小游戏 | 手势 | 产出 | 反馈动画 | 调性 |
|---|---|---|---|---|
| 🪵 敲木鱼 | 连点木鱼 | 攒功德 → 转好运 | "咚"声 + "功德+1"飘字 + 偶发金光暴击 | 解压·招牌记忆点 |
| 🫧 戳穿霉运泡泡 | 戳爆飘动泡泡（泡上写"水逆/脱发/被裁"等） | 戳爆数 → 好运 | 泡泡"啵"裂 + 迸好运光点 + 烦恼消散 | 解压·把烦恼具象化爆掉的疗愈 |
| 🐟 投喂锦鲤 | 点击撒鱼食 | 喂饱 / 锦鲤跃龙门 → 好运 | 锦鲤抢食、跃出水面、水波金光 | 治愈·可爱 |

**核心循环不依赖具体是哪几个游戏**，框架钉死即可（新增/替换游戏只是加组件）：

- **可插拔的「助力小游戏」统一接口**：
  - 输入：玩一局；
  - 输出：产出多少好运点 + 一段反馈动画。
- 新增小游戏 = 实现这个接口、加一个组件，**不改主循环**。
- 第一版做 **3 个**小游戏，但务必**共用同一套框架**，避免每个都做成半成品。（验证"可插拔"其实 2 个就够，3 个是为了首发的新鲜度与丰富度——这是有意识的取舍，不是过度设计。）

## 八、账号与身份（采纳 C：匿名优先）

- **匿名优先**：进来即给匿名身份（游客 token），**玩和助力零门槛**——朋友点开链接能立刻送好运，中间不卡登录。
- **要存战利品时再绑定**：仅当需要**保存福气卡 / 回赠 / 查看好运等级**时，才引导绑定（第一版绑定只接**微信授权**一种）。
- 此时用户已有沉没成本，转化率高。

## 九、平台与技术形态

- **第一版：H5 + Next.js**（套用仓库 `next开发规范.md`），先把核心循环跑通、验证玩法成立。
- 验证成立后再考虑**微信小程序**（裂变体验更好）。
- **数据结构第一版为"广场"和"小程序迁移"做最小预留**：心愿带"是否公开""标签"字段即可。**热度值/排序权重等字段先不建**（YAGNI，第一版不消费就别加，用到再说）。

## 十、模块划分（设计为可独立理解、可独立测试的单元）

| 模块 | 职责（单一） | 对外接口 | 依赖 |
|---|---|---|---|
| 身份模块 | 匿名 token / 微信绑定 | `当前用户`、`绑定` | — |
| 心愿模块 | 心愿/众筹的创建、状态、归属 | `创建心愿`、`查心愿`、`改状态` | 身份 |
| 好运经济模块 | 好运的产出、赠予、累加、达成判定 | `攒好运`、`送好运`、`查好运槽` | 心愿、身份 |
| 助力小游戏框架 | 统一的"玩一局→产出好运+动画"接口 | `玩一局(游戏id)` | 好运经济 |
| 福气卡模块 | 抽卡、稀有度、图鉴、回赠(仅重复) | `开卡`、`图鉴`、`回赠` | 身份 |
| 广场模块 | 公开心愿的发现/浏览（治理第一版最简） | `刷广场`、`送好运` | 心愿 |
| 成就模块 | 好运达成证书、好运等级/锦鲤值 | `生成达成卡`、`查等级` | 好运经济、心愿 |
| 分享模块 | 海报/链接/柔性文案生成 | `生成分享物料` | 心愿、成就 |

> 状态机原则：心愿状态（许愿中 → 已达成）流转必须**显式校验当前状态合法**，禁止隐式副作用。

## 十一、状态与错误处理（遵循 CLAUDE.md 四态模型）

- 所有异步流程至少四态：`idle → loading → success / error`。
- **空状态**必须明确：广场无内容、图鉴未解锁、心愿列表为空都要有专门的空态文案（且符合温暖治愈调性）。
- **error 态可重试**，且重试**不产生脏数据**（送好运、开卡等写操作必须幂等）。
- 写操作（送好运、开卡、回赠）**必须处理失败分支，禁止静默吞错**。

## 十二、第一版范围（MVP）

**做：**

1. 匿名身份 + 微信绑定（仅在存战利品时触发）。
2. 发起心愿（绑定心愿文案，需攒满 N 点好运）。
3. 助力小游戏框架 + **3 个**小游戏：**敲木鱼 + 戳穿霉运泡泡 + 投喂锦鲤**（见第七节）。
4. 好运经济：自己攒 + 他人送，均不限时；好运槽累积；达成判定。
5. 送好运的三入口：广场、给好友送、分享自己心愿。
6. 福气卡：抽卡 + 稀有度 + 图鉴 + 回赠（仅重复卡）+ **零挫败收集保底**。
7. 好运达成证书（梗图/仪式感）+ 好运等级累积。
8. 广场（陌生人互祝，第一版核心）+ **最简治理**（关键词过滤 + 事后人工，不建完整举报体系）。

**范围分层（辩论后调整为"先验证有趣，再铺开双向"）：**

> 📌 **最终路径（2026-06-22 确认）：分两步，先做有趣的小验证，再上完整双向。** 不再"全量首发"——因为"有趣"是增长赌注的命门，要先用最小成本把它验证透。

- **V0 · 有趣验证（先做，最快路径）**：把"**1-2 个攒好运小游戏（先做透敲木鱼）+ 好运槽达成 + 开一张搞笑福气卡 + 可截图分享**"做到"真好玩、真想晒"。目标只验证一件事：**有没有人觉得好玩到愿意玩、愿意分享。** 暂不做广场、不做完整图鉴/回赠。
- **V1 · 完整双向（V0 有趣验证成立后）**：补齐到完整 slogan——3 个小游戏、福气卡图鉴 + 回赠、**送好运给别人（异步，不伪造真人）+ 广场 + 给好友送 + 分享心愿**。这一步把"捐赠者收获福气"那一侧完整做出来（甲方案）。
- **核心不可砍**（任何版本都得有）：匿名身份、许愿、小游戏框架 + 至少 1 个真有趣的游戏、好运经济、达成反馈、开福气卡。
  > 与原"全量首发"的区别：不是砍功能，而是**调顺序**——先用 V0 验证"有趣"，避免在"好不好玩还没数"时就投入做全套广场/图鉴/回赠。双向（送好运/广场）是 V1 必做，不是被砍。

**先不做（明确砍掉 / 延后）：**

- 微信小程序（验证后再说）。
- 福气卡合成 / 交易 / 加成。
- 解锁更高级心愿（D）。
- 排行榜（C 的延伸，可二期）。
- 一切签到 / streak / 每日额度。

## 十三、初始数值（暂定，全部可调，但第一版必须有一组能跑的值）

> 设计意图：让"单次坐下来就能独自达成一个小愿"，体感不拖沓、不逼肝。

| 参数 | 初始值 | 设计意图 |
|---|---|---|
| 小愿所需好运 | 99 点 | 有"凑整 99"的玄学仪式感，又不至于遥远 |
| 自攒每局产出 | 单局约 12–20 点 | **自攒约 5–8 局即可独自达成**，单次会话内可完成，满足"急需" |
| 他人单次赠予 | 一次送 3–10 点 | 比自攒单点效率略低，但**带情感价值**；送几次就能明显帮到对方 |
| 福气卡获得 | **每送好运给他人约 3 次开 1 张卡**；**每积福 10 次必得 1 张"未拥有"卡（保底）** | 福气卡**只经"给予"获得**；保底实现"零挫败收集"，杜绝"永远差一张" |
| 稀有度比例 | 普通 / 稀有 / 传说（比例待定，但**不靠极低掉率制造稀缺**） | 只分"惊喜/好笑程度"，不制造肝不出的痛苦 |

> **两条开卡路径互不混淆**：① 福气卡——靠"送好运给他人"的积福获得（上表）；② 好运达成纪念卡——发起者达成心愿时获得 1 张（属运气侧，见第四节 B，不计积福、不进福气卡图鉴）。

## 十四、已定决策 + 仍待敲定的开放项

### 已定决策

1. **MVP 路径 → 先 V0 验证有趣，再 V1 上完整双向**（替代原"全量首发"，见第十二节与第〇节）。双向（送好运/广场）是 V1 必做、非砍。
2. **防滥用 → 接受"第一版弱防刷"**：仅做基础频率限制；广场防 bot 延后到有量时再做。两条硬规则现在就定：
   - **自己不能给自己的心愿送好运**（否则"被 N 人祝福"的情感价值失真）。
   - 匿名用户也能送，但同一匿名身份对同一心愿的赠予有基础频率限制。
3. **梗图/表情包版权 → 自创梗 + 热梗 并用**。落地护栏（必须遵守，否则是真实法律风险）：
   - **主力用自创梗**（原创卡面/文案/形象），版权自有、最安全；
   - **热梗以"二创/致敬"方式引用**：避开明确受版权保护的具体形象（如他人 IP 角色），避开明星/真人肖像，避开商标 logo；
   - 引用的网络热梗优先选**已广泛流传、无明确权利人**的通用梗式，存疑的一律改自创。

### 仍待敲定（不阻断开发，实现期再细化）

1. **匿名身份持久化**：游客清缓存 / 换设备会丢失匿名身份。需明确未绑定前的好运槽、已许心愿在身份丢失后的归属与提示文案（"四态"兜不住的真实数据丢失场景）。
2. **广场内容治理**：第一版用最简**关键词过滤 + 事后人工**，不建完整举报治理体系；违规/不当心愿的判定边界实现期细化。

## 十五、验证标准（Goal-Driven）

- **核心循环跑通**：能完整走一遍"发起心愿 → 自己攒 + 他人送 → 达成 → 得证书 + 送出方得福气卡"。
- **零焦虑校验**：全程**无任何**倒计时、签到、每日额度、过期失败提示。
- **零门槛助力**：未登录用户点开分享链接能**立刻**送好运成功。
- **四态完整**：主要页面都有 idle/loading/success/error + 空态。
- **写操作幂等**：重复送好运 / 重复开卡不产生脏数据。
